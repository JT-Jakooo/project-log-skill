# 写作原则与质量门禁

> 这些原则是从多次真实项目复盘报告的用户迭代反馈中提炼的硬规律。撰写全程对照本文件。

## 8 条写作原则

1. **读者视角优先** — 报告是给别人看的，不是开发者/当事人自留日志。避免内部黑话、过程噪音（如"PowerShell 报错重试"），只写读者需要理解的因果。

2. **实事求是** — 所有内容可追溯：标明依据（记忆文件、文档、交付物）。回忆不起/检索不到的地方明确标注「待补充」，**禁止编造**。

3. **去技术化** — 区分两类内容：
   - "AI 本来就能自动完成的"（实现细节、函数名、内部工具流程）→ 不写或一句带过；
   - "读者自己需要掌握的"（方法论、决策理由、关键参数）→ 保留。
   技术结论只保留读者判断所需的部分。

4. **结构连贯** — 迭代/测试/版本演进**融入历程叙事**，让读者感受到"变化与升级"，不并列堆砌成独立章节。

5. **成果要有证据** — 关键能力不能只"宣称"，要形成证据链：教学原文/来源截图 → 参数表 → 成品对照图 → 总结。读者能自行验证，报告才可信。

6. **数字具体可核** — 保留关键数字与口径（如"迭代 4 次"、"23 页、0 透明"、"用时 3 天"），不做模糊描述；数字来自真实记录，不估算。

7. **可视化保真** — 预览图用**真实产物导出**（如 PowerPoint 导出 1920×1080 PNG），不用近似渲染；截图要真实对应文中描述。图片控制体积，上传格式 `<img path="@./...">`。

8. **成果附使用教程** — 成果类报告必须给出"输入什么 → 输出什么"的使用说明（4-6 步），让读者能用起来，而不只是知道"有这个东西"。

## 常见取舍参考

| 情况 | 处理 |
|---|---|
| 用户只说"做个总结" | 按默认读者（分享给他人）+ 默认结构（四大部分）直接做，不问多余问题 |
| 用户明确只要日志 | 历程为主，经验/成果简写，但保留单文档不拆分 |
| 用户要求"再精炼" | 保留关键数字与结论，砍执行细节和重复段落；表格行数压缩（如 25 行→14 行） |
| 优化/修改记录 | 不设独立章节，融入历程；用户单独要"纯迭代清单"时再单独提炼 |

## 交付前自检清单（逐项核对）

- [ ] 素材可追溯：每个关键事实有来源；缺失处已标「待补充」
- [ ] 读者视角：无内部黑话、无过程噪音，去掉"AI 能自动完成的"细节
- [ ] 单文档完整：简介/历程/经验/成果四大部分齐全，未拆分
- [ ] 历程叙事：迭代融入阶段，读者能感受到升级
- [ ] 数字可核：关键数字带口径，无编造
- [ ] 证据链：核心能力有原文/参数/成品对照（学习型项目必查）
- [ ] 可视化保真：预览图为真实产物导出，压缩到位，caption 无英文双引号
- [ ] 使用教程：成果类已给出输入→输出步骤
- [ ] 篇幅：精简版与标准版之间，无冗余段落
- [ ] 文档已回读验证：标题层级、表格、图片、特殊字符渲染正确
